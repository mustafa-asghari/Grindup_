# Patch Note: SEC-004

## Worker personality

Security Worker - Paranoid Threat Hunter.

## Issue

Contest and lobby chat message endpoints allowed any authenticated user to read or post messages for a known contest or lobby ID, and message responses exposed sender email addresses.

## Root cause

The GET and POST handlers checked only for a signed-in session before querying or creating chat messages. They did not verify contest/lobby creator or participant membership, and both response selections included `user.email`.

## Original proof example

```bash
curl -i http://localhost:3000/api/contests/<contestId>/messages \
  -H 'Cookie: <authenticated non-participant session>'
curl -i -X POST http://localhost:3000/api/contests/lobbies/<lobbyId>/messages \
  -H 'Cookie: <authenticated non-participant session>' \
  -H 'Content-Type: application/json' \
  --data '{"message":"unauthorized hello"}'
```

## Original fix location

- `apps/web/src/app/api/contests/[contestId]/messages/route.ts`, GET and POST handlers.
- `apps/web/src/app/api/contests/lobbies/[lobbyId]/messages/route.ts`, GET and POST handlers.

## Original what to change

Require contest/lobby participant or creator membership before read/write, and remove sender email from selected response fields.

## Files changed

- `apps/web/src/app/api/contests/[contestId]/messages/route.ts`
- `apps/web/src/app/api/contests/lobbies/[lobbyId]/messages/route.ts`
- `Agents/stat.json`
- `Agents/patches/SEC-004.md`

## Fix made

The patch changed the exact original fix locations. Both route files now check creator-or-participant membership before message reads and writes. Contest chat authorizes `Contest.createdById` or `ContestParticipant`; lobby chat authorizes `ContestLobby.createdById` or `ContestLobbyParticipant`. Both message response selections now include only `id`, `name`, and `image` for the sender.

## Why this fix is minimal

The change keeps the existing message route shape, database models, and authenticated-user behavior, adding only the missing authorization guard and removing the sensitive `email` field.

## Result

Expected non-participant GET/POST requests now return `403 Forbidden` before message queries or creates. Authorized responses no longer include sender email addresses.

## Compatibility notes

Participants and creators/hosts remain authorized. Clients reading sender `id`, `name`, or `image` are unaffected; any client relying on sender `email` must stop using that private field.
