# Patch Note: SEC-003

## Worker personality

Security Worker - Paranoid Threat Hunter

## Issue

Any authenticated user could submit a `subjectId` to `POST /api/subjects/delete` and delete the global `Subject` row.

## Root cause

The route checked only `session.user.id`, then called `prisma.subject.delete({ where: { id: subjectId } })`. `Subject` is global while per-user enrollment lives in `UserSubject`, so deleting a subject could cascade shared topics, exercises, homework, vectors, and other users' enrollments.

## Original proof example

```bash
curl -i -X POST http://localhost:3000/api/subjects/delete \
  -H 'Cookie: <session>' \
  -H 'Content-Type: application/json' \
  --data '{"subjectId":"<other-subject-id>"}'
```

## Original fix location

`apps/web/src/app/api/subjects/delete/route.ts`, `POST`, around lines 14-23.

## Original what to change

Scope the action to the current user's `UserSubject` row or add explicit owner/admin authorization.

## Files changed

- `apps/web/src/app/api/subjects/delete/route.ts`
- `Agents/stat.json`
- `Agents/patches/SEC-003.md`

## Fix made

The patch changed the exact original fix location. The route now deletes only `UserSubject` rows matching both `session.user.id` and the submitted `subjectId` via `deleteMany`; it no longer deletes `Subject`. If no scoped enrollment exists, the route returns `404` with `Subject enrollment not found`.

## Why this fix is minimal

It preserves the existing endpoint, method, required body, success response, and page revalidation while removing the destructive cross-user/global delete. It does not introduce a new admin or ownership model.

## Validation attempted

```bash
pnpm --filter @grindup/web exec eslint src/app/api/subjects/delete/route.ts
pnpm --filter @grindup/web exec tsc --noEmit --pretty false
python3 -m json.tool Agents/stat.json >/dev/null
```

All three commands passed. The original curl proof was not rerun because it requires authenticated session cookies and seeded multi-user subject data.

## Result

Regular authenticated users can remove only their own enrollment. Global subject records and other users' enrollments remain intact.

## Compatibility notes

Existing successful callers still receive `{ "success": true }`. Callers that were relying on this route to globally delete shared subjects now receive a scoped unenrollment behavior instead.
