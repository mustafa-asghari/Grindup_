# Patch Note: REL-005

## Worker personality

Reliability Worker - Production SRE

## Issue

Compose runner execution failed because executor containers could not see the source files generated by the runner container.

## Root cause

The runner created files in a temp directory inside the runner container, then asked the host Docker daemon to bind-mount that container-internal path into a sibling executor container. The host daemon could not resolve that path to the generated files.

## Original proof example

```bash
curl -sS -i -m 15 -X POST http://127.0.0.1:8080/execute -H 'Content-Type: application/json' -H 'X-Runner-Token: dev-only-runner-secret' --data '{"code":"def solution(x):\n    return x","language":"python","test_cases":[{"id":"t1","input":"x = 1","expected_output":"1","is_hidden":false}],"time_limit_ms":2000,"memory_limit_kb":256000}'
```

## Original fix location

`compose.yml` runner service volumes/environment around lines 80-86; `apps/runner/services/docker_service.py` `DockerService.run_code` around lines 23-50.

## Original what to change

Use a host-visible execution work directory shared with the runner container, or use Docker volumes/archive-copy so executor input files are visible to sibling containers.

## Files changed

- `apps/runner/services/docker_service.py`
- `compose.yml`
- `Agents/stat.json`
- `Agents/patches/REL-005.md`

## Fix made

Changed the exact original fix locations. `DockerService` now creates per-run temp directories under `RUNNER_EXECUTION_WORKDIR` when configured, maps that per-run directory to `RUNNER_EXECUTION_HOST_DIR` for the Docker bind mount, and falls back to the previous `tempfile.mkdtemp(prefix="grindup_run_")` host-direct behavior when neither env var is set. Cleanup still removes only the per-run temp directory.

`compose.yml` now configures `RUNNER_EXECUTION_WORKDIR=/tmp/grindup-runner-work`, `RUNNER_EXECUTION_HOST_DIR=${RUNNER_EXECUTION_HOST_DIR:-/tmp/grindup-runner-work}`, and bind-mounts `${RUNNER_EXECUTION_HOST_DIR:-/tmp/grindup-runner-work}:/tmp/grindup-runner-work` into the runner.

## Why this fix is minimal

The patch changes only file staging and compose wiring for executor bind mounts. It does not change runner authentication, request/response contracts, executor images, timeout cleanup, or concurrency behavior.

## Result

The proof curl returned HTTP 200 with `{"status":"accepted"}` and one passing visible test result. The previous `python3: can't open file '/app/main.py'` error did not reproduce.

## Compatibility notes

Host-direct runner behavior is preserved when `RUNNER_EXECUTION_WORKDIR` and `RUNNER_EXECUTION_HOST_DIR` are unset. Existing chmod behavior remains in place so the executor `coder` user can read and write generated files.
