# Patch Note: VAL-001

## Worker personality

Validation Worker - Input Gatekeeper

## Issue

Problem descriptions from third-party scrape data could reach `dangerouslySetInnerHTML` without sanitisation.

## Root cause

LeetCode `question.content` was persisted as raw HTML and later rendered directly in the problem panel.

## Original proof example

Set a local problem description to `<img src=x onerror=alert(document.domain)>` and open `/problems/<problem-id>`.

## Original fix location

`apps/web/src/components/editor/problem-panel.tsx` `ProblemPanel` line 121; `apps/web/src/app/api/problems/scrape/route.ts` around description persistence.

## Original what to change

Add a shared HTML sanitizer with a narrow allowlist and render only sanitized problem statements.

## Files changed

- `apps/web/src/lib/html-sanitizer.ts`
- `apps/web/src/components/editor/problem-panel.tsx`
- `apps/web/src/app/api/problems/scrape/route.ts`
- `apps/web/package.json`
- `pnpm-lock.yaml`
- `Agents/stat.json`

## Fix made

Added `sanitizeProblemHtml` using `sanitize-html` with an allowlist for problem-statement formatting, code/pre blocks, lists, tables, safe links, HTTPS/HTTP images, and limited MathML tags. The policy strips event handler attributes, style/script content, `javascript:`/`data:` URLs, and excludes unsafe tags such as iframe, object, embed, and SVG.

`ProblemPanel` now memoizes the sanitized description and passes only that value to `dangerouslySetInnerHTML`. The scrape route now sanitizes `q.content` before Postgres description writes, testcase extraction, embedding text, and ClickHouse `content` insert.

This patch changed the exact original render and scrape persistence locations. The shared helper and package files were added because no first-party sanitizer dependency/helper existed.

## Why this fix is minimal

The change leaves the existing HTML rendering model intact for legitimate problem formatting while adding a single shared boundary before the unsafe DOM sink and before new scraped content is stored.

## Validation attempted

- `pnpm add sanitize-html @types/sanitize-html --filter @grindup/web` completed.
- `pnpm --filter @grindup/web exec tsc --noEmit --pretty false` passed.
- Node probe against the compiled helper sanitized `<img src=x onerror=alert(1)>`, `<a href="javascript:alert(1)">`, and `<script>`; the output had no `onerror`, `javascript:`, or `script`, and preserved an HTTPS image.
- `pnpm --filter @grindup/web build` passed.
- `pnpm --filter @grindup/web lint` failed on existing repo-wide lint debt, including many pre-existing `no-explicit-any`, React hook, and unescaped entity errors.
- Targeted `eslint src/lib/html-sanitizer.ts src/components/editor/problem-panel.tsx` had no errors; it reported the existing unused `motion` warning in `ProblemPanel`.

The original browser proof example was not manually rerun against a seeded local problem row during Worker implementation.

## Result

Existing problem descriptions are sanitized immediately before rendering, so stored hostile HTML is made inert at the browser sink. Newly scraped problem content is also sanitized before persistence to Postgres and ClickHouse.

## Compatibility notes

Common LeetCode-style statement tags remain allowed, including paragraphs, headings, emphasis, code/pre blocks, lists, tables, links, HTTPS/HTTP images, and limited MathML. Inline styles, classes, SVG, iframes, objects, embeds, scripts, event attributes, data URLs, and relative image URLs are removed.

The lockfile was already dirty before this task; running `pnpm add` updated the sanitizer entries and may also reflect existing workspace dependency drift.
