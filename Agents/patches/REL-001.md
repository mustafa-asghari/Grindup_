# Patch Note: REL-001

## Worker personality

Reliability Worker - Production SRE

## Issue

Timed-out runner containers were killed but not removed, leaving stopped executor containers on the host.

## Root cause

`DockerService.run_code` returned immediately after `container.kill()` in the timeout branch, before the success-path `container.remove()` call could run.

## Original proof example

```bash
Submit an infinite loop with time_limit_ms=100 then run docker ps -a --filter ancestor=grindup-executor --filter status=exited.
```

## Original fix location

`apps/runner/services/docker_service.py` `DockerService.run_code` around lines 44-84.

## Original what to change

Move container removal into a finally using `remove(force=True)`.

## Files changed

- `apps/runner/services/docker_service.py`
- `Agents/stat.json`
- `Agents/patches/REL-001.md`

## Fix made

The patch changed the exact original fix location. `run_code` now tracks the created container outside the inner execution `try` and removes it in a `finally` block with `container.remove(force=True)` whenever container creation succeeded.

## Why this fix is minimal

The change only moves container cleanup into the lifecycle path shared by success, error, and timeout returns. It keeps the outer `temp_dir` cleanup unchanged and does not alter result tuple shapes or timeout message text.

## Validation attempted

- `python3 -m py_compile apps/runner/services/docker_service.py` - passed
- `python3 -m json.tool Agents/stat.json >/dev/null` - passed

The original proof example was not rerun because this Worker pass did not start the runner service or execute Docker workloads.

## Result

Execution containers are now removed after normal completion, exceptions after container creation, and timeout returns.

## Compatibility notes

Successful, errored, and timed-out executions keep the same returned tuple shapes. Timeout responses still return `("", "Time Limit Exceeded (<limit>ms)", <limit>)`.
