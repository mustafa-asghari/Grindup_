# Patch Note: VAL-003

## Worker personality

Validation Worker - Input Gatekeeper

## Issue

Multipart import and homework uploads could reach `arrayBuffer()`, parsers, OCR, OpenAI, and database paths before server-side file size and type limits were enforced.

## Root cause

The upload handlers trusted the multipart `File` object until extraction time; import checked size only after buffering, and homework had no server-side file size/type gate before extraction.

## Original proof example

`dd if=/dev/zero of=/tmp/big.bin bs=1m count=200` then submit it as `file` to `/api/import` or `/api/homework/submit`.

## Original fix location

`apps/web/src/app/api/import/route.ts` and `apps/web/src/app/api/homework/submit/route.ts` before extraction helpers.

## Original what to change

Check `file.size`, extension, and MIME before `arrayBuffer`, cap extracted text, and reject unsupported files.

## Files changed

- `apps/web/src/app/api/import/route.ts`
- `apps/web/src/app/api/homework/submit/route.ts`
- `Agents/stat.json`
- `Agents/patches/VAL-003.md`

## Fix made

Added route-level and helper-level upload validation in both multipart handlers before `file.arrayBuffer()` or extraction work. Files over 10 MB now return `413`, and unsupported or MIME/extension-mismatched uploads now return `400`.

Follow-up patch added a pre-`request.formData()` multipart body-size gate in both routes. When a multipart request declares `Content-Length` above `MAX_UPLOAD_BYTES + 1MB`, the route now returns `413` before invoking the multipart parser; missing or invalid `Content-Length` is ignored and the existing per-file `File.size`/type checks remain the authoritative backstop after parsing.

Accepted server-side file types are limited to PDF, common raster images (`png`, `jpg`, `jpeg`, `webp`, `gif`), and UTF-8 text/Markdown (`txt`, `md`). Homework no longer treats binary `doc`/`docx` files as parseable text because the existing logic only attempted UTF-8 decoding.

Import file extraction now caps extracted text at 100,000 characters before downstream AI, topic, embedding, and storage paths. Homework extraction and grading/storage input are capped at 50,000 characters, matching the existing stored-content limit.

The patch changed the exact original fix locations: the multipart branches now preflight uploads before calling `fileToText` or `extractTextFromFile`, and both extraction helpers enforce the same guard as a backstop.

Follow-up validation cleanup removed targeted ESLint blockers in the VAL-003 files only: dead import/variable cleanup, `unknown` catch handling with safe message extraction, local AI-plan typing, Prisma callback inference, and `const` for an unchanged subject display name. Upload guard behavior was not changed.

## Why this fix is minimal

The change keeps the existing extraction flows for supported PDFs, images, TXT, and MD files, but adds small boundary checks before expensive or memory-heavy work. It does not introduce new dependencies, alter route shapes, or change unrelated upload/UI code.

## Result

Oversized multipart uploads with a too-large `Content-Length` are rejected with `413` before `request.formData()`. Oversized parsed files are rejected with `413` before `arrayBuffer()`, parser, OCR, OpenAI, or Prisma work starts in the route logic. Unsupported uploads are rejected with `400` before extraction work, and extracted text is capped before downstream AI/database use.

## Compatibility notes

Normal PDF, image, TXT, and MD uploads stay supported. `application/octet-stream` is tolerated when the filename extension is supported, but explicit MIME values must match the supported extension family. Binary `doc`/`docx` uploads now fail fast instead of being decoded as unreliable text.
